# 0001 — Deterministic record ids instead of uuid4

Status: accepted
Date: 2026-09-06

## Context

The memory layer exists so that three strategies — `RecentTurnsMemory`,
`RetrievalMemory`, `ConsolidatingMemory` — can be compared against each other
on LongMemEval. Two of the reported numbers are retrieval precision and
recall, which are computed by asking which stored records a strategy actually
pulled into the model's context. `Retrieval.sources` carries those ids back.

That comparison only means something if the same input produces the same ids
every time. The evaluation replays a history more than once: once per
strategy, and again whenever a run is repeated. If ids differ between runs,
the sets being compared are not addressing the same records, and precision and
recall stop being comparable — silently, since the numbers still compute.

`uuid4` was proposed first, and it is wrong for this: it is random, so it
gives a different id to the same turn on every replay.

## Decision

Record ids are derived from position: `f"{session_id}:{turn_index}"`, built by
`make_record_id()` in `life_agent/agent/memory.py`. `session_id` names the
conversation and `turn_index` counts records within it, so an id is a function
of where a record sits in the history and nothing else.

`MemoryRecord.id` is supplied by the caller rather than generated by the
store, so a replay harness controls it directly.

A summary produced by consolidation gets an id in the same scheme and records
what it consumed in `derived_from`, which keeps traceability through a
compaction step.

Ids must never grow a random component. Content hashing —
`hash(session_id, turn_index, content)` — is an acceptable variant, since it
is also a function of the input.

## Consequences

A replayed history is addressable. The evaluation can name a record, ask
whether a strategy surfaced it, and get the same answer tomorrow.

Ids are not globally unique. Two different conversations that happen to use
the same `session_id` collide, and a caller that reuses a `turn_index` within
one session overwrites meaning without any error being raised. Nothing
enforces this; `ConversationAgent` maintains its own counter, and any other
caller must too.

Ids leak structure. `s1:4` says which session and which position, so an id
printed in a log or a report reveals the shape of the conversation. This is
acceptable for a local single-household tool and would not be for a shared
service.

The default `session_id` in `ConversationAgent` is derived from the clock, so
an ordinary chat session still gets a unique one without the caller thinking
about it. Determinism is available on demand rather than by accident: the
evaluation passes the id in.
